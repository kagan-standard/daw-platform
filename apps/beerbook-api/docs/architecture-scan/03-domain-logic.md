# Phase 3 — Domain logic (lib and process-event engine)

**Scope**: `lib/*.js` and Supabase Edge Function `process-event` (engine + index). One paragraph per lib module; process-event event types, idempotency, invocation points, Node vs Deno parity.

---

## Lib modules

**actorIdentity** — Resolves the acting identity for ratings: either an authenticated user (from JWT claims set by softAuthMiddleware) or a guest when `ENABLE_GUEST_RATINGS` is true. Validates client-provided guest IDs (UUID v4 format, header `X-Guest-Id` or body `guest_id`) and exposes `resolveActor()`, `actorMiddleware`, and `validateGuestId`. Used by POST/DELETE ratings and guest-claim flows; responds with 401/400 and `AUTH_REQUIRED` or `INVALID_GUEST_ID` when resolution fails.

**achievementProgress** — Computes progress toward achievement rules for a user. Maps achievement `subtype` and `rules` to internal metrics (e.g. `total_ratings`, `unique_styles`, `unique_venues`, `review_min_len`, `stars_gte`/`stars_lte`, `yg_gte`/`yg_lte`/`yg_eq`, `distribution_yg`, `cheers_given`/`cheers_received`, `streak_weeks`, `price`) and derives a numeric target from rules (count, gte, min_count, buckets, etc.). Uses PostgREST to count ratings, ledger rows, or distinct fields and returns `{ progress_current, progress_target, remaining }`. Used by the Node process-event engine for `rating_submitted` achievement evaluation.

**adminValidation** — Centralized request validation for admin API. Provides async validators for challenges (create/patch: week_start/week_end Monday UTC, title, description, target_count, reward_label, reward_badge_id), achievements (create/patch: key slug, name, description, category_key, subtype, trigger_type, rules with target, difficulty, reward_tabs, is_hidden), achievement categories (create/patch), featured beers (create/patch: beer_name, week_start/week_end, feature_type, etc.), cosmetics (create/patch: key, type, rarity, unlock_type, tab_price, border_fit, etc.), and sync `validateBeerPatch` (catalog beer: name, brewery_name, style, abv 0–30). Used by `routes/admin.js` to keep handlers thin and enforce contract in one place.

**catalogMap** — Maps a raw beer row from PostgREST/Supabase to the catalog browse and detail API shape. Normalizes numeric fields (abv, IBU, flavor scores, review breakdown), exposes `reviews` (aroma, appearance, palate, taste, overall, count), backward-compat aliases (`review_aroma`, etc.), and optional `power_score` (global_elo), `comparison_count`, and `style_elo`. Used by GET `/api/catalog/browse` and GET `/api/catalog/beer/:id`.

**crewAuth** — Shared crew membership guard. `requireCrewMembership(rest, userId, crewId)` fetches `crew_members` and returns the membership row or null. Used by crew-scoped feed, stats, and activity endpoints to enforce consistent membership checks before returning crew data.

**crewMilestones** — Emits crew milestones after a new rating is created. Uses RPC `crew_rating_counts_for_user` to get per-crew totals; emits `crew_total_ratings` at thresholds 25, 50, 75, 100 (idempotent via unique constraint on crew_id, type, data key). For ratings with `venue_id` and `locationVerified === true`, checks if this is the user’s first rating at that venue and emits `first_venue_visit` per crew. Optionally emits `member_streak` when `currentStreakWeeks` (from process-event) crosses 5 or 10. Inserts into `crew_milestones`; 409 is treated as idempotent success.

**elo** — Elo engine for head-to-head beer comparisons. Initial rating and K-factor configurable via env (`ELO_INITIAL`, `ELO_K_MATURE`, `ELO_K_NEW`, `ELO_MATURITY_CAP`). `getOrCreateBeerElo(rest, beerId)` fetches or inserts `beer_elo_ratings`; `updateEloAfterComparison(rest, winnerBeerId, loserBeerId, resultId)` computes new Elos with maturity-based K, PATCHes both beers, and optionally writes `beer_elo_events`. Skips when either beer id is null (e.g. name-only ratings). Used after head-to-head result creation in the ratings flow.

**headToHead** — Head-to-head comparison feature: cooldown, challenger selection, and prompt creation. Validates cooldown (no offer if user has a prompt in last `HEAD_TO_HEAD_COOLDOWN_HOURS`). `getChallengerRating` finds a same-user rating in the same style family (via `styleFamily.styleToFamily`) or same beer_id with YG within tolerance; `createPromptAndBuildPayload` inserts `head_to_head_prompts` and returns API payload; `maybeOfferHeadToHead` orchestrates cooldown check, challenger lookup, and prompt creation. Used by POST ratings response to optionally attach a head-to-head offer; reward tabs configurable via `HEAD_TO_HEAD_REWARD_TABS`.

**keycloakAdmin** — Keycloak integration for user lifecycle and auth. Obtains service-account token (`getAdminToken`), creates users in realm `daw` (`createUser`), handles ROPC token grant and refresh (`getTokensForUser`, `refreshTokens`) with typed error handling (invalid credentials, email not verified, account disabled), and sends verification email (`sendVerificationEmail`). Uses `KEYCLOAK_URL`, `KEYCLOAK_ADMIN_*`, and `KEYCLOAK_MOBILE_CLIENT_ID`. Used by auth and admin routes.

**processEvent** — Invocation layer for process-event. When `PROCESS_EVENT_URL` or `SUPABASE_URL` is set, POSTs to the Edge Function URL with Keycloak JWT and JSON body (`event_type`, optional `event_id`, `payload`); otherwise calls the in-process handler registered via `setInProcessHandler` (used when self-hosted with no Supabase Edge). Optional `INTERNAL_PROCESS_EVENT_SECRET` is sent in body for the in-process path. Returns normalized `{ unlocked, tabs_delta, tabs_balance, current_streak_weeks, longest_streak_weeks }` or throws with status/body. Used by server.js (rating_award, rating_submitted) and activity routes (cheers_given, cheers_received).

**processEventEngine** — In-process process-event engine (Node). Same event semantics as the Edge Function engine: `rating_award` (weekly cap via RPC `award_rating_tabs_with_cap`, idempotent by event_id), `cheers_given`/`cheers_received`/`admin_grant` (single ledger insert, idempotent by event_id; cheers_received requires `payload.target_user_id`), `rating_submitted` (evaluate achievements via `achievementProgress.calculateAchievementProgress`, unlock via RPC `unlock_achievement_with_rewards`, mint tabs only when not already unlocked). Uses `rest` and `totalFromContentRange`; returns same result shape as Edge. `achievement_unlock` and `spend` are no-ops. Admin check via `ADMIN_USER_ID`/`ADMIN_USER_IDS`.

**ratingsValidation** — Validation for rating `yg_value`. `validateYgValue` enforces the canonical set: `-1`, or `1`–`10` in **0.5** steps (`2x` integer), with `0` rejected; uses a small epsilon on the half-step grid to tolerate float noise but does not round off-grid values into compliance (aligned with `ratings_yg_value_check` and `20260330100000_ratings_yg_value_canonical_half_steps.sql`). `ygValueToStarRating` maps canonical YG to internal integer stars `1`–`5` via the locked linear formula (DB/legacy only; not user-facing). Used by rating create/update handlers before persisting.

**styleFamily** — Canonical style families for filters and counts. `styleToFamily(style)` maps free-text style names to one of nine families (IPA, Pale Ale, Lager, Stout, Porter, Wheat, Pilsner, Sour, Belgian) or 'Unknown' using substring rules (e.g. porter→Porter, kölsch→Pale Ale, steam→Lager). `styleDistributionToFamilies` collapses a style→count map to family→count and returns top family. Used by catalog/filter logic and headToHead challenger matching.

**tabs** — Tabs economy and profile helpers. `ensureProfileExists` / `ensureUserTabsProfile` create or fetch profile and user_tabs_profile; weekly reset when week_start rolls. `calculateRatingComponents` derives earn components (base, location, photo, price, review) for rating rewards; `awardTabsForRating` applies tier/seeder/new-beer multipliers, inserts `tab_transactions`, and patches user_tabs_profile (deprecated path; production rating rewards use process-event). `awardTabsForCheers` is deprecated in favor of process-event; `awardTabsForBeerApproval` still used for new-beer approval. Tier multipliers from `tier_requirements`.

**uploadModeration** — Async post-upload moderation. `runModeration(rest, userId, filePath, url)` is intended to be run after the upload response is sent (e.g. setImmediate). Skips HEIC; for Vision-supported formats calls `visionModeration.checkSafeSearch`. If unsafe: deletes file, clears `profiles.avatar_url` and `ratings.photo_url` matching the URL, and inserts `tab_notifications` (photo_removed). Uses `UPLOAD_DIR` for filesystem path.

**visionModeration** — Google Cloud Vision Safe Search for images. `checkSafeSearch(filePath)` returns `{ safe }`; flags LIKELY/VERY_LIKELY for adult, violence, racy. When `MODERATION_ENABLED` is false or `GOOGLE_APPLICATION_CREDENTIALS` is unset, returns safe. Supports JPEG, PNG, WebP; `isVisionSupportedFormat` used by uploadModeration to skip HEIC and unsupported types.

## Process-event (Edge Function + engine)

**Event types** — `rating_award`, `cheers_given`, `cheers_received`, `rating_submitted`, `achievement_unlock`, `admin_grant`, `spend`. Implemented and side-effectful: `rating_award`, `cheers_given`, `cheers_received`, `admin_grant`, `rating_submitted`. `achievement_unlock` and `spend` are accepted but no-op in both runtimes.

**Idempotency** — Ledger events (`rating_award`, `cheers_given`, `cheers_received`, `admin_grant`) require a client-supplied `event_id` (UUID). Duplicate event_id results in unique constraint violation (PostgREST 409 or PG 23505); engine returns zero tabs_delta and does not throw. For `rating_submitted`, idempotency is at achievement level: `unlock_achievement_with_rewards` uses INSERT/ON CONFLICT; already-unlocked achievements do not mint tabs again.

**Invocation points** — (1) **In-process (self-hosted)**: `server.js` registers the in-process handler at startup via `setInProcessHandler`, wiring to `internalRoutesModule.handleProcessEventRequest` with `rest`, `totalFromContentRange`, and `getKeycloakUserId`. `invokeProcessEvent` is then used from server.js after rating create (`rating_award` with BFF-generated event_id, then `rating_submitted`) and from `routes/activity.js` for cheers (`cheers_given` and `cheers_received` with per-call event IDs). (2) **HTTP to Edge**: When `PROCESS_EVENT_URL` or `SUPABASE_URL` is set, `invokeProcessEvent` POSTs to the Supabase Edge Function with the caller’s Keycloak JWT. (3) **Internal HTTP**: POST `/internal/process-event` (when `INTERNAL_PROCESS_EVENT_SECRET` is set) accepts Keycloak JWT and `x-internal-secret`; same validation and engine as in-process, used for server-to-server or testing.

**Node vs Deno parity** — The Node engine (`lib/processEventEngine.js`) and the Edge engine (`supabase/functions/process-event/engine.ts`) share the same event routing, ledger semantics, admin checks, and result shape. **Difference**: For `rating_submitted`, the Node engine uses `achievementProgress.calculateAchievementProgress` and supports the full set of achievement metrics (total_ratings, unique_styles, unique_venues, review_min_len, stars_gte/lte, yg_gte/lte/eq, distribution_yg, cheers, streak_weeks, price). The Edge engine uses a smaller evaluator set in `engine.ts` (`EVALUATORS`: `checkin_count`, `time_window_checkin`) and does not use the same progress/threshold logic; achievement unlocks in production are therefore driven by the Node path when the BFF uses the in-process handler. When the BFF calls the Edge Function (e.g. hosted Supabase), `rating_submitted` achievement evaluation on the Edge is limited to those evaluators unless the Edge engine is updated to mirror the Node achievement logic.

---

## Summary

Domain logic is split across 16 lib modules (identity, achievements, admin validation, catalog mapping, crew auth/milestones, Elo, head-to-head, Keycloak, process-event invocation/engine, ratings validation, style family, tabs, upload/vision moderation). The process-event pipeline is dual-path: in-process (Node) for self-hosted and HTTP to Supabase Edge when configured. Idempotency is enforced by event_id on tabs_ledger and by achievement-unlock semantics; Node and Edge engines are aligned for ledger events and admin checks, with a known parity gap for `rating_submitted` achievement evaluation (full metrics only in Node).
