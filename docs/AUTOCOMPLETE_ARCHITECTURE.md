# Beer Autocomplete Architecture

## Canonical Implementation

- Frontend listener and dropdown rendering: `apps/beerbook/app.js` in `bindBeerAutocomplete()`
- Frontend API call wrapper: `apps/beerbook/supabase.js` in `DB.searchBeers(q)`
- Backend endpoint (canonical search source): `apps/beerbook-api/routes/beers.js` in `GET /api/beers/search`

## Request Path (End-to-End)

1. User types in `#beer-name` input on the Rate form (`apps/beerbook/index.html`).
2. `bindBeerAutocomplete()` in `apps/beerbook/app.js` debounces input and calls `DB.searchBeers(q)`.
3. `DB.searchBeers(q)` in `apps/beerbook/supabase.js` sends `GET /api/beers/search?q=...`.
4. `GET /api/beers/search` in `apps/beerbook-api/routes/beers.js` queries the catalog table via PostgREST:
   - `GET /beers?...`
5. Returned rows are mapped to autocomplete items and rendered in the dropdown in `app.js`.

## Database Table Used

- Catalog source table: `beers` (catalog table; this is the active equivalent of historical `ref_beers` naming)
- This endpoint must not be limited to `ratings` table results.

## Regression History (Why This Doc Exists)

- Autocomplete has repeatedly regressed when search logic was changed to ratings-only or split across multiple fallback paths.
- Prior changes sometimes fixed one layer (frontend or backend) while another path still used older logic.
- Permanent guardrail:
  - `apps/beerbook-api/routes/beers.js` contains:
    - `IMPORTANT: Autocomplete must search ref_beers catalog. See bug history — do not change this without testing.`

## Build/Overwrite Notes

- `apps/beerbook-api` runs directly with `node server.js` (no transpile/generation step in `apps/beerbook-api/package.json`).
- Frontend files in `apps/beerbook` are mounted as static assets in Docker (`infra/compose/docker-compose.yml`), not generated by a build pipeline.
- If regressions happen again, investigate code changes, not generated output.
